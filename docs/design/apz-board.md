# apz-board: one Rust core for the board, on the desktop and in the browser

This crate implements the parts the web and desktop apps must agree on exactly. It does it once, in Rust. The
desktop links it natively. The web loads it as WebAssembly (`wasm32-unknown-unknown` + `wasm-bindgen`). This was
the owner's decision on 2026-10-13. It replaced the TypeScript `board-layout.ts`, `nav-*.ts`, `ground.ts` and
`lift-ctrl.ts` (all deleted in `987394f`), and the partial Rust copies that lived in the desktop's `floor3d/world/` (also gone).

## Scope

**In the crate** (pure logic, no rendering, no I/O, deterministic):
1. **Hardware boards.** Parse `assets/hardware/board/*.json` and its `parts/`, and compute each resting part's
   world box and top surface. Rendering still builds meshes from the same JSON in each app, so this is about
   geometry facts, not drawing.
2. **Board layout.** Place slots, terraces (plates), columns, rooms (their footprints and floor heights),
   gangways, lifts and homes for N agents. Apply `boardScale`. The output is a `Layout`.
3. **Walk surfaces** (`docs/design/walk-surfaces.md`). The layout emits a list of walk surfaces and links. Plates,
   columns, landings, bridges and the lift cab are generated from it, so they rest on drawn tops by construction.
4. **Nav graph.** Rasterise the walk surfaces into the grid (cells, heights, components, drop edges, portals)
   and plan paths with A* over it. Also a fine height field for feet (0.05).
5. **Motion.** The `NavWorld` step: robots, commit-point invariants, separation, yield and hold, gravity, jump
   and drop, respawn, lift riding.
6. **Lift controller.** Queue, capacity, doors and travel.
7. **Audits.** Grounding (nothing floats or sinks), z-fight (no coplanar overlaps among generated surfaces), and
   nav invariants (`onWall`, `hover`, reachability). These run as the crate's own tests and are callable from the
   apps' debug hooks.

**Not in the crate (yet):** rendering, robot rigs and clips, room furniture generation (`rooms/gen`),
behaviour-engine decisions (what a robot wants to do next; it calls `navigate_to` on the crate), labels and
cameras. Room *footprints and floors* are in the crate; their furniture is drawn by each app inside the
footprint and must stay inside it, which the crate's audit checks. Furniture and the behaviour engine can move
into the crate later.

## Shape

```
crates/apz-board/                  the logic; `std`, no threads, no I/O; f64 math; serde for inputs/outputs
  src/hardware.rs  layout.rs  walk.rs  grid.rs  plan.rs  motion.rs  lift.rs  audit.rs  lib.rs
crates/apz-board-wasm/             wasm-bindgen wrapper (cdylib); thin; builds apps/web/src/wasm/apz_board*.js+.wasm
apps/desktop                       depends on apz-board directly
```

**API** (the same names on both sides):
- `Board::from_assets(models: &AssetSet, kind) -> Board`: the assets are embedded in the crate with
  `include_str!` from `assets/hardware`, so both apps get the same data with no I/O.
- `layout(board, &LayoutInput { agents: [{id, role, seat_hint}], gpus, scale_cap }) -> Layout`. `Layout` holds
  the slots, plates, columns, rooms, gangways, lifts, homes, walk surfaces, links and scale, and is serde-serialisable.
- `World::new(&Layout, seed) -> World`
- `world.add_robot(id, species_traits { floats, radius, step, jump, drop })`
- `world.navigate_to(id, goal)`, `world.set_home(id, x, z)`
- `world.step(dt)`: fixed step, deterministic.
- `world.robots()`: the poses `(x, y, z, yaw, mode, clip)` for the renderers.
- `world.lifts()`: the cab and door states.
- `world.audit()` and `world.debug_cell(x, z)`.

**Web boundary** (performance matters; see the profiling report):
- The `World` lives in WASM memory. The web reads robot poses through a `Float32Array` view over WASM memory,
  with no per-frame allocations and no JSON in the frame loop.
- `step` takes `dt` and returns nothing heavy. `Layout` crosses the boundary once per board build, as a plain
  JS object via serde-wasm-bindgen.

**Determinism:** the fixed step, a seeded RNG and no hash-map iteration order in outputs make the same input
give the same output on both targets. Golden fixtures (`assets/nav/fixtures.json` and the new
`assets/board/fixtures.json`) are generated by the crate and checked on both sides.

## Migration

1. Build the crate with its own test suite. It ports the logic from the TS sources and folds in the walk-surface
   rules, and it is validated by the audits rather than by matching the old TS output byte for byte. The old
   output had the bugs the owner reported.
2. The web swaps `board-layout.ts`, `nav-*.ts`, `ground.ts` and `lift-ctrl.ts` for the WASM module behind the
   same call sites (done: the web loads this crate through `apz-engine-web`; the TS files and `floor3d/board-core.ts` are
   deleted). The renderers consume `Layout` and robot poses.
3. The desktop swaps `world/board_layout.rs`, `layout.rs` and `motion.rs` for the crate.
4. The old TS and Rust copies are deleted. The web test suite keeps its rendering-side tests and calls the crate
   for logic; the logic tests live in the crate (`cargo test -p apz-board`).
5. Web build: `apps/web/build.mjs` runs
   `cargo build -p apz-board-wasm --target wasm32-unknown-unknown --release` and then `wasm-bindgen`. It copies
   the `.wasm` (fingerprinted) into `dist`. The size target is under 400 KB gzipped (wasm-opt when available).
